## 二、★★ 推翻上一版结论：「三买失效」是错的

上一版说「三买胜率 35.7%、平均 -4.15%，建议降级」。**这个结论不成立。**

真实数据（1200 只标的、5 日窗口、剔除未走完的近期信号）：

| 信号 | 样本 | 胜率 | 平均收益 | 中位收益 |
|---|---|---|---|---|
| **3buy/strong** | 738 | **86.2%** | **+7.75%** | +5.94% |
| **3buy/weak** | 105 | **20.0%** | **-4.31%** | -3.73% |
| 1buy/strong | 608 | 90.1% | +6.67% | +4.80% |
| 2buy/normal | 332 | 91.6% | +6.78% | +4.74% |

**三买是所有买点里质量最高的一档**，不是最差的。

### 根因：weak 三买是「观察态」，被当买入信号统计了

`kind=3buy, level=weak` 的语义是「已向上突破中枢上沿，但回抽尚未确认」——
它根本不是买入信号，只是提醒「这只票在突破中，留意」。
但因为两者 `kind` 同为 `3buy`，按 kind 聚合时混进了同一张表。

### 已排除的三个混淆

1. **不是大盘拖累**：weak 样本全在 2026-09，但当月全市场等权均值仅 **-2.35%**，
   远小于 weak 平均 -4.31%。
2. **不是中枢太小**：按中枢振幅分档，`<5%` 胜率 84.8%、`10-20%` 胜率 70.0%，
   没有单调关系。
3. **不是时段巧合**：strong 三买在 11 个月里**每个月**都是 70%+ 胜率，稳健。

## 三、★★ 顺带修掉两个真 bug

### 3.1 弱三买报的是「当日最高价」——现实中买不到

```
605179  2026-09-23  信号价 31.48
        当日 O 29.30  H 31.48  L 27.04  C 27.09← 冲高回落 -14%
```
逐例核查 5/5 案例 `信号价/当日最高 = 1.000`。
那是事后挑出的最贵价位，用它当「买入价」在任何回测里都是错的。

已改为**信号日收盘价**，并把置信度从 0.5 降到 0.4，`reason` 里写明价格口径。

### 3.2 signal.level 是猜的，不是引擎给的

```python
# 旧：按 confidence 硬猜
"strong" if s.confidence >= 0.75 else "normal"
```
弱三买 confidence=0.5 → 被存成 `normal`，于是「弱三买」在库里**伪装成普通三买**。
后果：按 level 分档时根本找不到 weak 样本，
这正是上一版误判「三买没有弱档、整体失效」的直接原因。

已改为直接取引擎的 `s.level`。

## 四、★★ 一个必须记住的统计陷阱：回测的「信号价」是选择偏差

同一批信号，两种起算口径（1200 只真实样本）：

| 信号 | 按信号价胜率 | 按收盘价胜率 |
|---|---|---|
| 1buy/strong | 99.5% | 90.1% |
| 2buy/normal | 100.0% | 91.6% |
| 3buy/strong | 99.9% | 86.2% |
| 3sell/strong | 0.5% | 9.5% |

「按信号价」几乎全部接近 100%。**这不是策略有多准，是幸存者偏差**：
买点报价取的是回调笔的**最低点**，卖点取的是反弹笔的**最高点**，
都是事后才知道的极值。实盘按收盘下单，拿不到这个价。

⇒ **唯一可用于实盘决策的口径是「按收盘价」。**
`scripts/diag_3buy.py` 每次运行都会打印这张对照表和这段警告。

## 五、可复现性验证：120/120 完全一致

M8 验收标准「任意历史日重放出的信号与当日实际生成完全一致」，
以2026-10-08 那次全量重扫为基线：**120 只标的，逐条 (kind, ts) 完全吻合。**

### 途中发现的坑：取数窗口长度会改变笔结构

同样 `as_of=2026-10-08`，只改喂给引擎的 K 线根数：

| 根数 | 笔数 | 三买位置 |
|---|---|---|
| **250**（生产口径） | 18 | 2026-02-11 ✅ 与库内一致 |
| 251 | 19 | 2026-01-21 ❌ 漂移 |

多一根 K 线就多出一笔 → 中枢边界变化 → 「离开中枢」的笔位置变化 → 信号日期漂移。

这不是前视偏差，而是分型/笔算法对输入长度的固有敏感性。
**可复现的前提是取数口径必须冻结。**
`scripts/run_replay.py:PROD_KLINE_LIMIT = 250`，
并有测试守着它与生产脚本 `duck.get_daily(code, 250)` 保持一致。

### 另一个坑：库里其实只有一次基线

全库 1129 条信号的 `created_at` **全部是 2026-10-08** ——
信号系统从未逐日累积运行过。所以用「某历史日当天实际生成的信号」当基线在多数日期是空的。
`replay_day` 已改为以 `ts <= D` 全量作基线，并在报告里记录基线来源，
避免把「无基线」误报成「不可复现」。

### 前视偏差的直接检验

`verify_no_lookahead()`：截断未来数据后若**凭空多出**信号，即为前视偏差。
正常情况是信号变少（未完成的笔被重绘），不是变多。

## 六、每日随机抽查

```
python scripts/daily_spotcheck.py --n 8                # 抽 8 条看推理链
python scripts/daily_spotcheck.py --label 4135 --label-value correct
python scripts/daily_spotcheck.py --stats              # 打标 vs 实际结果对照
```

卡片展示：信号类型+档位 / 置信度 / **判定理由** / 当时结构快照
（K线数、笔数、中枢区间、背驰数、引擎版本）/ 当时市场状态。

三条设计约束：
1. **随机而非全量** —— 全量看会不自觉只挑看着对的；`sample` 在全池里抽，不是先 LIMIT 再抽。
2. **先冻结、后看结果** —— 卡片刻意不包含前向收益，并提示「不要去看后续涨跌」。
3. **打标可追溯** —— 每次变更写 `event_log`，谁在何时标了什么可查。

`--stats` 输出「人工判断 vs 实际结果」对照：
**标correct 却实际亏损 = 推理与结果脱节，该查因子权重/口径，而不是继续调参数。**

## 七、遗留问题

1. **历史基线缺失**：信号表只有一次全量重扫。要积累真正的逐日基线，
   需让信号任务按交易日连续运行至少 1 个完整月。
2. **DuckDB 文件锁**：同步/测试同进程互斥，导致部分测试在同步期间失败
   （非代码缺陷）。根治需改为「单写进程 + 只读副本」。
3. **M8 ③消息—行情联动**：等分钟线同步完成后跑真实统计。
4. **旧数据的 level 需要重算**：修正前的 1129 条信号 level 是错的，
   重跑一次信号任务即可覆盖（`INSERT OR IGNORE` 不会覆盖，需先清 `signal` 表）。
