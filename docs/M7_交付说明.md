## 一、本轮解决的最大障碍：模型可用性

### 1.1 ollama pull 在本机网络下不可用（根因查明）

**症状**（5 次尝试全部同样表现，累计浪费约 12GB 带宽）：

| 观察 | 数据 |
|---|---|
| 主文件 | 已预分配完整大小（4.4GB），但 20 秒内**零增长** |
| 16 个 `-partial-N` 分片 | 全部只有 **57~68 字节** |
| `OLLAMA_MAX_PARALLEL=1` | 完全一样 |

**结论**：不是并发问题、不是残片问题 —— **ollama 的分片下载机制在这个网络环境下根本工作不了**，没有任何分片在真正传输。

### 1.2 替代路径（已打通）

| 源 | 结果 |
|---|---|
| `registry.ollama.ai` | 分片卡死 |
| `huggingface.co` / `hf-mirror.com` | **均不可达**（15 秒超时） |
| 阿里云 / 腾讯云 registry | 401 / 000 |
| **`www.modelscope.cn`（阿里）** | ✅ **可达，10.4MB/s** |

下载命令：
```bash
curl -L -C - -o model.gguf \
  "https://www.modelscope.cn/api/v1/models/{org}/{model}/repo?Revision=master&FilePath={file}"
```

### 1.3 GGUF 分片合并：字节拼接 ≠ 格式合法

下载到的是 `xxx-00001-of-00002.gguf` + `xxx-00002-of-00002.gguf`。

**踩坑过程**：
1. 简单字节拼接 → 字节数与官方版完全一致（4683074240），但 ollama 仍报
   `Error: split GGUF must use llama.cpp split filename pattern`
   —— 因为 metadata 里`split.count=2` 标记还在
2. 尝试用 Python `gguf` 库合并 →连续踩了5 个坑：
   - `add_kv` 方法名不存在（实际是 `add_key_value`）
   - `field.parts[0]` 是长度前缀不是值（标量字段有 4~5 个 parts）
   - 量化 tensor 需要**字节 shape** 而非元素 shape（3584 vs 3594）
   - memmap 无法直接 `struct.pack`
   - 15 万 token 的数组重写代价过高
3. **最终用官方工具** `llama-gguf-split.exe --merge` —— 一次成功，339 个 tensor
   （与 `split.tensors.count` 完全一致）

**结论**：私有二进制的合并不要自己逆向，用官方工具。类似金十的 WebSocket。

### 1.4 Windows 上 `Path.resolve()` 会规范化大小写

```python
Path('models/Qwen2.5-7B-Instruct-Q4_K_M.gguf').resolve()
# → .../models/qwen2.5-7b-instruct-q4_k_m.gguf   ← 全小写！
```
NTFS 大小写不敏感，`resolve()` 返回磁盘实际存储的大小写。Modelfile 里
指向了另一个文件，导致「明明改了却没生效」。**必须用 `absolute()`**。

## 三、★ prompt v1.0→ v1.1：一个静默失效

### 现象

首轮真实打标 6 条，**关联个股全部为空（0/6）**。连「山东港口青岛港：
外贸航线数量持续增加」这种明确提到公司的消息都识别不出。

### 根因

原 prompt 只给模型 **800 个股票代码**（不给名称），并规定
「无法确定则给[]，宁可为空也不要错」。模型无法把消息里的「青岛港」
对上 `601298`，于是按规则返回空列表。

**更糟的是它不报错** —— 打标流程正常完成，置信度 0.5，只是内容为空。

### 修法

让模型输出**公司名称**而非代码，由本地 `stock_index`（5948 个别名）
做名称 → 代码映射：

```json
"related_names": ["青岛港"]   // 消息里真实出现的公司名
```

理由：模型**记不准代码**（说「茅台」会给 002049 紫光国微），
但**认得出公司名**；本地映射 100% 准确。

### 效果

| 消息 | v1.0 | v1.1 |
|---|---|---|
| 山东港口青岛港：外贸航线增加 | `[]` | **`['601298']`** ✅ |
| 贵州茅台三季度营收下滑12% | `[]` | **`['600519']`** ✅ |
| 央行征信管理局迎来新局长 | `[]` | `[]` ✅（确实没提公司） |
| 比特币跌破82000美元 | `[]` | `[]` ✅（非A股） |

## 四、交易日历（★解除长期阻塞）

### 数据来源：从本地日线反推

137 万行日线里每天都有 5000+ 只成交，**有成交必然开市**。
比任何在线节假日表都准 —— 它反映的是「实际上是否开市」。

### 三态设计（本轮最重要的修正）

早期实现两态（1/0），把所有「日线没出现过的日期」写成 `is_open=0`。
这对**已发生**日期正确，但对**未来**日期是灾难：

> 日历覆盖到明年后，**明年所有任务会被永久静默跳过，且不报任何错**。

修正为三态：

| 值 | 含义 | 运行时处理 |
|---|---|---|
| 1 | 交易日（有日线证实） | 直接返回 True |
| 0 | 已确证休市 | 直接返回 False |
| **-1** | **未来未知** | 周末→False；工作日→指数探针→仍未知则推断为True 并标注 |

实测：316 交易日 / 526 已确证休市 / 365 未来未知，判定验证 7/7 通过。

### 指数实时探针

- 新浪 `klc_td_sh.txt` 是**自定义加密串**（508B，base64 解码后仅 38% 可打印）
  → 逆向成本高且随版本失效，不做
- 腾讯指数接口：交易日返回**当日时间戳**（如 `20261008161500`），
  休市日返回上一交易日时间戳。比较日期即可判定，**517ms**
- **限制**：只能判「当天」，不能判未来

## 五、调度器（附录 6.1 全部 11 类任务）

### 关键机制

| 机制 | 实现 | 实测 |
|---|---|---|
| 交易日守卫 | 休市跳过算 `ok=True skipped` | 周六执行 → skipped |
| **超时熔断** | 守护线程 + `join(timeout)` | 5秒任务限1秒 → **1.1秒返回** |
| 失败重试 | 指数退避，最多 3 次 | 3 次后放弃 |
| 补跑机制 | 按「窗口内触发点 + 未成功记录」 | 不按下次触发时间 |
| 执行日志 | 每次写 `event_log` | ✅ |

### ★ 超时熔断曾形同虚设

原实现靠任务内部 `check()`，但**check 在任务末尾才执行** ——
4 秒任务限 1 秒，实际跑了 4 秒。**检测到了超时但没拦住**。

根因：任务卡在无check 点的网络请求里。改为守护线程后，
主线程超时即放弃等待（调度链不阻塞）。

### ★ 休市日跳过应算成功

否则每周末与节假日产生一堆「失败」告警，真问题被淹没。

### ★ 修掉一个影响可读性的 bug

纯文本邮件中文之间全是空格 —— `美  股：纳  指 +  0  .  8  2  %`。

根因：`"  ".join(_cell(c) for c in row)` 把**已拼好的字符串**
当成可迭代对象按字符拆开。改为按类型分派，并加 `_display_width()`
（CJK 按 2 列计）让分隔线对齐。
