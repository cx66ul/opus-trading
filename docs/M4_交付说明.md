## 一、七个构件（M4 清单逐项对应）

| 构件 | 函数 | 实现要点 |
|---|---|---|
| ① 包含处理 | `merge_klines` | 处理方向由「前一根与再前一根比较」决定；记录 `i0/i1` 原始索引区间 |
| ② 分型 | `find_fractals` | 中间 K 线的高/低均为三根极值|
| ③ 笔 | `build_bi` | 双标准：新笔（间隔≥4）/ 老笔（间隔≥1） |
| ④ 线段 | `build_segment` | 连续三笔同向重叠；`strict="strict"` 时缺口打断 |
| ⑤ 中枢 | `build_zhongshu` | 连续三笔重叠区间；延伸/扩展/新生 |
| ⑥ 背驰 | `detect_beichi` | MACD 柱面积度量 + **面积门槛过滤** |
| ⑦ 三类买卖点 | `scan_signals` | 一买/二买/三买 + 对称卖出点，每条带 reason 与 confidence |

**两套坐标系**（这是本实现最关键的工程决策）：
- `start_i / end_i` → **合并 K 线序列**下标，用于结构定位
- `start_raw / end_raw` → **原始 bar 序列**下标，用于 MACD 面积计算

早期版本只保留前者，导致背驰比值出现 `0.0` / `25.156` 这类无意义值。

## 四、开发中修掉的真实缺陷

### 1. 坐标系错位（最隐蔽）
`Bi.start_i` 是合并序列下标，而 MACD 按原始 bar 序列计算。
两者混用导致背驰比值出现 `0.0`（区间太窄）与 `25.156`（错位偏移）。
**修复**：`Bi` 增加 `start_raw/end_raw` 字段，两套坐标系并存。

### 2. 方向性错误（最严重）
`scan_signals` 里写的是 `bis[k]` vs `bis[k+1]`，而**笔严格交替** ——
这等于「拿下跌笔和反弹笔比面积」，方向都不同，比值毫无意义。
**修复**：改为比较同向笔列表中相邻的两个（中间隔一根反向笔），
并让 `Beichi` 记录 `cur_bi_idx/prev_bi_idx`，调用方无需反推。

### 3. 背驰面积无门槛
分母过小（a1=0.063）会爆表，分子为 0 表示该波段无正面积。
**修复**：加 `MIN_BEICHI_AREA = 1.0` 双向门槛。
真实数据实测（51 个样本）比值中位数 1.30、最大 22.55 ——
大比值是真实强反弹，不该用比值上限误伤。

### 4. Beichi 不可哈希
dataclass 默认不可 hash，`set(beichis)` 报 `unhashable type`。
**修复**：改用 `dict[bi_idx, Beichi]`。

## 五、黄金用例编写原则（可复用到M5~M9）

这一轮我改对了 4 个用例、也改错了 3 个，总结出的原则：

1. **构造数据必须先手工推演一遍**，不能凭感觉写。
   错例：我曾用 `(9,11)` 表示「向下包含」—— 但 `(9,11)` 的 low 高于 `(10,8)`，
   根本不构成包含。引擎是对的，用例是错的。

2. **断言位置要写清索引含义**。
   错例：包含处理的结果在 `merged[1]`（被包含的两根合并），我写成 `merged[0]`。

3. **每个用例都要写「为什么这样构造」**，失败时能立刻分辨是引擎错还是用例错。

4. **平台形态不构成分型** —— 连续相同 (high,low) 会被合并掉。
   极值处必须是「高-更高-高」或「低-更低-低」三根。
