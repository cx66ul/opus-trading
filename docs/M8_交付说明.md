## 二、★ 最有价值的发现：3buy 明显失效

真实数据（2026-10-08 全市场信号，5 日窗口，按方向分开）：

| 类型 | 样本 | 买点胜率 | 平均收益 | 卖点胜率 | 平均收益 |
|---|---|---|---|---|---|
| **1buy** | 38 | **100.0%** | **+10.47%** | — | — |
| **2buy** | 35 | **100.0%** | **+9.37%** | — | — |
| **3buy** | 28 | **35.7%** | **-4.15%** | — | — |
| 1sell | 54 | — | — | 98.2% | -10.15% |
| 2sell | 36 | — | — | 100.0% | -10.63% |
| 3sell | 52 | — | — | 100.0% | -8.47% |

**结论**：
- 一买、二买质量很高（100% 胜率、+10% 收益）
- **三买是失效的**（35.7% 胜率、-4.15% 收益）

缠论原典里三买是「趋势延续确认」——突破中枢后回抽不破。
本实现把它当成了「最强的买点」，但实测数据说明它更像**追高确认**。

**这个发现只有回测能给出**。信号生成时三类买点看起来一样"强"，
用户也无从判断。但一旦按类型统计胜率，差异立刻暴露。

**下一步建议**（需要你决定）：
- 方案 A：暂时降级三买（推荐列表里排除），只保留 1buy/2buy
- 方案 B：检查三买的判定逻辑 —— 是否把「回抽不破」写成了「突破」
- 方案 C：提高三买的确认要求（如要求站上中枢上沿 N 日）

## 三、★★ 一个统计陷阱：买卖方向混算胜率毫无意义

首版实现把买卖混在一起统计，得到：

```
143 条信号 → 胜率 87.4%（看起来极准）  平均收益 -3.3%
```

**这两个数字自相矛盾** —— 若 87% 的信号方向正确，平均收益不可能为负。

**根因**：买点 65 条 / 卖点 78 条。卖点「命中」的定义是**跌了**，
而这些股票在卖点之后多在下跌，于是：
- 卖点命中率高（98%+）
- 买点收益率低（+6% 但 18% 亏）
- 混合后胜率被卖点拉高，收益被买点拖低 → 互相抵消

**修正**：`aggregate_stats` 改为按 buy/sell 分开统计，
顶层 `winrate` 字段保留但语义明确为「买点视角」。

这个坑很隐蔽：单看胜率 87.4% 只会觉得"策略很准"，
不会有人去质疑它。

## 四、★★ 我自己犯的错：测试污染了生产数据

`test_append_only` 的清理逻辑是：

```python
c.execute("UPDATE signal SET eval_json = NULL")   # ← 没有 WHERE
```

**把 243 条真实回测结果全清掉了**，而且**没有任何报错** ——
清空是合法 SQL，测试通过、数据没了。

真实回测数据不可再生（需要重新跑一遍 243 次 K 线查询）。

**修正**：每个用例先快照自己改动的行，`finally` 里精确还原。
已恢复 242 条（1 条被测试借用后正确还原）。

这类污染比代码 bug 更危险 —— 代码 bug 会报错并被修复，
数据污染是**静默且不可逆**的。

## 五、★ 归因方向判反会让优化走错路

初始实现的判断条件写反了：

```python
if lost <= market_ret * 1.5:   # ← 错
    return "大盘拖累"
```

实测：**大盘跌 6%、个股跌 5.2%**（个股其实跑赢 0.8%）
被判成「消息误判」。

正确条件应是 `lost >= market_ret * 1.05`（个股跌幅≥ 大盘跌幅）。

**为什么这个方向必须对**：
- 判对了 → 大盘拖累 → 知道这是系统性风险，不该调 prompt
- 判反了 → 消息误判 → 以为是 LLM 判断问题 → **错误地去调 prompt**

归因方向的错误会把优化引向完全错误的环节。

修正后实测：

| 场景 | 归因 |
|---|---|
| 个股跌 5.2%，大盘跌 1.0% | 消息误判 ✓ |
| 个股跌 5.2%，大盘跌 6.0% | 大盘拖累 ✓ |
| 个股跌 4.0%，板块跌 5.0% | 板块退潮 ✓ |
| 个股跌 2.0%，中途涨过 2.5% | 止损过紧 ✓ |

## 六、附录 5.4 的样本量保护已落地

样本 < 10 时 `winrate` 返回 **None**（不是 0 也不是 1），
并在 `winrate_note` 里说明原因。

实测效果：

| 样本 | 显示 |
|---|---|
| 9 条 | **不显示** |
| 10 条 | 显示 |

这直接对应附录那句警告：「1 单 1 胜 = 100%」是最危险的误导。
测试 `test_one_win_one_loss_not_100_percent` 固化了这个行为：
真实命中率存 `raw_hit_rate` 供内部使用，但 `winrate` 为 None。

## 七、其他修掉的工程缺陷

| 缺陷 | 修正 |
|---|---|
| `fetchone().rowcount` → AttributeError | 用 `cursor.rowcount` |
| 全胜场景 `sum(loss)/len(loss)` 除零 | `pl_ratio` 返回 None（无意义）而非崩溃 |
| 空方向返回的键集不一致 | 调用方按固定 key 读会 KeyError |
| `as_of` 可选 → 违反铁律二 | 改必填；注意不能放在有默认值参数之后 |
| DuckDB `DATE ?` 语法错 | 写 `CAST(? AS DATE)` |
| 空样本时格式化崩溃 | `avg_ret` 为 None 时不套数值格式 |
